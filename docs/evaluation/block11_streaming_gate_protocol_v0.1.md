# Block 11 Wearable Streaming Gate Protocol v0.1

**Date frozen:** 2026-10-25
**Purpose:** Decide whether the completed offline evidence justifies entering the conditional wearable streaming-prototype block
**New model fitting:** None
**Prototype execution:** None

## 1. Original entry condition

The project proposal permits a streaming demonstration only if a final justified offline model has interpretable and stable event performance. Block 8 separately required adequate wearable robustness. This assessment applies those existing conditions; it does not invent a new performance threshold after seeing results.

## 2. Evidence sources

Use only reviewed results already accepted in the repository:

1. direct two-channel wearable validation and descriptive test performance;
2. the Block 8 wearable robustness and deployability closeout decisions;
3. train-only temporal, enriched-feature, and causal-feature candidates;
4. corrected external PSG mechanism performance;
5. corrected multi-dataset label, scorer, and repeated-night uncertainty decisions; and
6. the recorded validation status of each candidate.

Hash every compact source file used. Do not select a favorable tolerance, membership set, participant subset, model, or data source during the assessment. Use each experiment's frozen primary row and final decision.

## 3. Required entry conditions

Enter a wearable streaming prototype only if all conditions are true:

1. **Wearable advancement:** a wearable candidate has passed its own independent advancement path rather than only train-development screening.
2. **Interpretable event performance:** accepted wearable event performance is not classified by its source experiment as unreliable or inadequate.
3. **Robustness:** the Block 8 wearable-robustness decision is supported.
4. **Causal confirmation:** a causal wearable event method has confirmation beyond the participant cohort used for method development.
5. **Boundary interpretation:** the proposed output can be represented honestly under the observed label uncertainty, without claiming exact physiological timing.

If any condition fails, record `no_go` for the streaming prototype. A no-go does not stop research on paired wearable transfer; it prevents software demonstration from being mistaken for detector readiness.

## 4. Required report

Record the exact evidence values, source paths and hashes, each condition outcome, the overall decision, the main limitation, and the next permitted research step. Do not benchmark latency or memory after a no-go because no final wearable model has entered the prototype stage.
